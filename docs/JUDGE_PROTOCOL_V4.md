# PolicyFlow 初赛严格盲审协议 v4

> 用途：以 GOAI Agent Infra 初赛的公开规则为基准，对提交材料做严格、可复核的盲审。本协议是项目内部质量门，不代表 GOAI 官方评审结论、官方分数线或任何具体个人的意见。

## 0. 公开信息边界

- GOAI 官网公开页面将 Agent Infra 相关人士列为“赛道专家与顾问”，**未将其公布为已确认评委名单**。不得假定任何专家必然参与评分，也不得按其个人偏好替代官方规则。
- 因其公开背景覆盖软件工程、AgentTeams、数据库、云原生与产品工程，本协议仅采用更严格的架构、可验证性、工程边界与落地性检查视角。
- 规则核对基准：GOAI Agent Infra 赛道页、35 页参赛手册、19 页初赛内容模板、官方直播纪要、Datawhale Baseline、FAQ 与提交页；版本和 SHA-256 见 `docs/OFFICIAL_SOURCE_AUDIT_2026-08-15.md`。若官方页面或表单更新，以提交时版本为准。
- 初赛侧重方向与方案设计，代码包可选；因此“没有真实集群运行”本身不是 P0。反之，材料一旦声称“已通过、已运行、已接入或已开源”，就必须提供相应层级的可定位证据。
- 云 Skills、Nacos、Higress、PolarDB、UnifiedModel、RocketMQ、LoongSuite、AgentScope Studio 与 AgentLoop 是推荐项；官方明确推荐项数量不计分。直播 FAQ 明确非云场景可用自定义 Skill。评委 Agent 不得把“未堆推荐工具”误判为硬性失败。

## 0.1 两阶段盲审纪律

1. **材料首轮**：只看 500 字介绍与最终 PDF/PPT，禁止读取源码补齐材料中没讲清的能力；先给出首轮分数与淘汰风险。
2. **证据复核**：再打开源码包，以全新临时目录运行入口、测试、Golden、Skill/CRD 校验并核对单 Run 回执；只允许提升有证据支持的分数。
3. **差值解释**：若首轮与复核分数相差超过 6 分，说明哪些核心证据仍藏在 ZIP 中，并把它们移入必交材料后重审。
4. **不读取历史高分**：每轮不得把先前模拟分数当先验；官方要求、当前成品和 fresh evidence 才是事实源。

## 1. 官方权重与评分纪律

评分仅按以下五项，不得以页面美观、技术名词数量、代码行数或潜在专家偏好替代：

| 维度 | 权重 | 严格审阅重点 |
|---|---:|---|
| 场景价值与行业可复制性 | 25 | 真实用户、明确痛点、价值收益、可迁移边界；PoC 指标与生产 ROI 必须分开 |
| 多 Agent 协同与自主闭环 | 25 | 不可互代职责、拆解、上下文、状态、异常与人机边界 |
| Skill 工程体系与生态复用 | 25 | 可复用契约、版本、失败、安全、复用与演进 |
| 工程落地、运行验证与安全可审计 | 20 | 可运行性、证据、权限、审批、回滚、审计与依赖边界 |
| 开放 / 开源贡献 | 5 | 协议、文档、示例、第三方披露与可访问性 |

每项需同时记录：`得分 / 可定位证据 / 最大反证 / 最小改进`。不得因推荐工具堆叠加分；评审只看必要性、接口契约、可替换性、迁移成本和端到端闭环。

## 2. 硬门槛（Must-pass）

任一失败即标记 `P0 / NO PASS`；但不得把官方初赛明确允许的“未提交可运行代码”错误判为 P0。

1. **提交有效性**：项目名符合表单约 20 字限制；介绍不超过 500 字；PPT/PDF 可打开、可读，版本号和交付物名称不冲突。
2. **真实多 Agent**：不少于 3 个不同职能 Agent；每个具有 Name、Role、Capabilities（能/不能）、Inputs、Outputs、Dependencies、Decision Boundary、Trace 八字段。不能以同一提示词换名、同一服务串行函数或单 Agent 多工具冒充协作。
3. **删除反事实成立**：删除 Planner、Executor、Verifier 或任一必要 Human 后，必须能说明哪项决策权、验证独立性或安全性质失效；若替换后行为与风险不变，按伪多 Agent 处理。
4. **AgentTeams 设计基线**：逐项映射角色编排、任务拆解、上下文传递、协同执行、状态追踪五项能力。CRD 静态兼容、部署设计、`agt apply`、Matrix 消息和真实 Worker handoff 必须分别标注，不得混称“已运行”。
5. **Skill 工程**：核心能力必须以 Skill 表达；每个核心 Skill 至少说明名称、用途、I/O、触发条件、依赖、失败处理、安全边界、复用关系与版本/回滚语义。
6. **上下文与恢复**：在 Agent memory、知识库/RAG、共享状态、Trace/可观测中至少实现或明确设计两项；说明跨 Agent 传递、持久化、恢复及权限边界。若不使用 RAG，须说明替代机制为何足够。
7. **高风险安全闭环**：写操作具备服务端权限边界、审批绑定 Run/Plan/Checkpoint/实际参数、独立验证、失败/拒绝回滚和审计；Executor 不得自批、自验或修改验证回执。
8. **主张—证据一致性**：所有“已通过/已运行/已接入/已开源”主张都能定位到材料页、代码路径、命令、回执或公开链接。PDF 摘要、ZIP 完整回执、测试结果、版本和场景边界不得冲突。
9. **诚实边界与权利**：Mock、合成适配器、静态校验、路线图、真实外部系统、模型/API、第三方依赖、许可证与开源可访问性均应明确；不得把 Mock、HMAC 演示、hash chain 或本地测试包装为企业 SSO、不可抵赖签名、真实生产接入或公开 Release。
10. **推荐工具口径**：必须列出 AgentTeams 与各推荐方向的真实状态、替代实现、稳定接口和迁移成本；未接入不构成 P0，虚假写成“已接入”构成 P0。

## 3. E0—E4 证据分级

同一主张取材料中最高且可定位的等级；未来计划不得高于 E0。

| 等级 | 定义 | 可接受证据 | 处理 |
|---|---|---|---|
| E0 | 只有断言或路线图 | “支持回滚”“可生产部署” | 不计为已完成 |
| E1 | 静态、可定位设计 | 架构图、Skill 契约、Identity、CRD YAML、完整回执文本 | 证明设计或一次声明，不单独证明运行 |
| E2 | 作者可复现 | 固定版本源码包、依赖说明、命令、自动测试、Golden、攻击用例 | 计入本地工程完成度 |
| E3 | 可独立核验 | 独立验证器、审计包 manifest、Trace 校验、真实工具回执、干净环境复跑 | 核心差异化主张的优先证据 |
| E4 | 外部或生产近似 | 公开 Release、真实 AgentTeams/Matrix handoff、外部沙盒、用户试用、第三方验收 | 强加分；无则如实披露 |

对“携证执行”等核心差异化主张，至少应有 E2，优先争取 E3。若必交材料只出现测试数字，至少需同时提供复跑命令、源码定位和单次 Run 的可读证据链；否则视为 E0/E1 营销数字。

## 4. 反营销与反伪多-Agent检查

1. 每个“生产、真实、自动、可验证、开源、兼容、接入”词语均要求紧邻 E1 以上证据；无证据则删改为设计或路线图。
2. 不按 Agent 数量计分，只计不可互代的权限、状态责任、输入输出和失败后果。
3. 不按推荐组件数量计分；Skill、MCP、RAG、OTel 等只有进入同一闭环且可说明必要性时才加分。
4. Mock 必须说明适配器类型、外部调用数、模拟的状态来源和不能证明的能力。
5. 每条审计声明必须区分计划参数、实际参数、工具回执和独立验证结果；只记录计划不得称为执行审计。
6. 若测试、回执、PPT、PDF、README 或 ZIP 中的版本、ID、计数、场景边界不一致，先降级证据，再决定是否 P0。

## 5. 安全主张专项检查

对高风险写操作逐项回答并能落到代码、契约或回执：

- Human 审批签署的是自然语言，还是具体 Run、Plan、Checkpoint、角色、有效期与实际参数 hash？
- ToolGateway 是否从规范持久化状态重新计算并校验参数，而非信任客户端传入的 `approved` 标记？
- 执行 Agent 是否被服务端阻止调用未登记工具、越权写入、伪造角色或自行验收？
- 政策更新、计划重建、checkpoint 变化、跨 Run Token 重放、参数替换、幂等键冲突和并发重复执行时会发生什么？
- 拒绝、崩溃、超时和人工撤销时，补偿/回滚是否幂等，是否再经独立状态验证？
- Trace/hash chain 的性质是否被准确表述为 tamper-evident，而非数字签名、WORM 或不可抵赖证明？

## 6. OTel、Skill、MCP 新增门槛

这些不是为了堆叠组件；一旦声称使用，必须满足对应最小证据。

### 6.1 OTel / 可观测

- 若声称 OTel/AgentScope/AgentLoop/LoongSuite 已接入，须给出 trace/span 语义、采集入口、Agent/Skill/MCP 关联方式、后端存储/检索和至少一个可查询样例。
- 仅有自定义 hash Trace 可计 Trace 审计，但不得称为 OTel 兼容或完整可观测平台。
- 至少说明 Trace、Log、Metrics 中已实现的类别与未实现项。

### 6.2 Skill

- Skill 版本必须与 Runtime/契约兼容；变更 I/O、权限、策略或回滚语义时必须提升版本并保持历史 Run 可读。
- Skill 的复用应在至少两个 Agent 或两个场景中展示稳定层与适配层；仅复制文件或换名不计复用。
- 核心 Skill 必须存在失败与拒绝路径测试，不得只展示 happy path。

### 6.3 MCP / 等价工具契约

- 使用 MCP 时：说明 server、transport、鉴权、Schema、工具白名单、错误处理、幂等、审计和最小权限。
- 未使用 MCP 时：说明等价协议、入口、I/O Schema、鉴权、失败/降级、审计及迁移到 MCP 的成本；不因未实现 MCP 自动扣为 P0。
- 工具契约必须由服务端执行，而非仅作为 LLM 提示词或前端表单校验。

## 7. 最严五分钟质询

1. 谁因该问题承担真实成本？当前断点、成功口径和迁移边界是什么？
2. 为什么不是单个 Agent 加工具？删除 Planner 或 Verifier 后新增何种风险？
3. AgentTeams 的五项能力分别落在哪个对象？哪些是 CRD 静态设计，哪些已 live 运行？
4. 两个场景共用了哪些 Skill/状态机/工具契约，只替换了什么 schema、政策或 adapter？
5. 审批为何绑定实际调用而非文本计划？更换参数、角色、Run 或 checkpoint 时为何无法重放？
6. 审计包如何证明实际执行而非计划执行？Verifier 为什么无写权限？
7. Skill 失败、升级和回滚后，历史 Run、回执和审计是否仍可读可验？
8. 哪些已完成，哪些只是 Mock、静态兼容或复赛路线图？

## 8. 停止条件

满足以下条件即建议冻结，不为追求额外技术名词而扩大未验证范围：

1. Must-pass 10/10，P0 为零；名称、介绍、PPT/PDF、ZIP、版本与哈希已冻结一致。
2. 所有运行数字有可复跑入口；任何改动代码、测试、依赖、场景或材料主张后，必须重新运行并重制回执。
3. 所有 Mock、静态兼容和外部依赖边界在介绍、方案、README 与回执中一致。
4. 当前阶段无法 fresh 验证的 Matrix、SSO、IAM、OTel、真实云服务或公开 Release，不得临近截止临时接入并宣称完成；保留为后续路线图。
5. 仅在不破坏上述一致性且能新增 E3/E4 证据时继续修改；否则提交当前通过版本。
