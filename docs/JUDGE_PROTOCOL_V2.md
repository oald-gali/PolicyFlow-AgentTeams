# PolicyFlow 初赛评委 Agent 协议 v2

> 用途：每完成一个交付阶段，以初赛材料可见证据为准进行反向复核。它是项目内部质量门，不代表 GOAI 官方评审结论，也不模拟任何具体个人评委的偏好。

## 1. 核对基准

- [GOAI Agent Infra 官方赛道页](https://www.goaihz.com/tracks?track=infra)
- [GOAI Agent Infra 参赛手册](https://oss.goaihz.com/prod/20260720/6e21b053-f18b-4857-83e2-835bd96d5434.pdf)
- [GOAI 初赛方案模板](https://oss.goaihz.com/prod/20260804/2e567d1a-99c1-45ce-8a0f-3d36d11f3314.pptx)
- [GOAI FAQ](https://www.goaihz.com/faq)

规则核对日期：2026-08-14。若提交页与本文不一致，以提交时官方页面和表单提示为准。

官方初赛评分权重：场景价值 25%、多 Agent 协作 25%、Skill 工程 25%、工程/安全/审计 20%、开源贡献 5%。评委 Agent 必须按同一权重评分，不得用界面美观或代码量替代核心维度。

## 2. Must-pass gates

任一项失败即记为 `P0 / NO PASS`，先整改，不进入概率乐观估计：

1. **提交格式**：项目名称按表单限制控制在 20 字以内；项目介绍不超过 500 个中文字符；方案 PPT 或 PDF 可正常打开。
2. **真实多 Agent**：至少 3 个职责不同的 Agent；不是同一提示词换名字，也不是单 Agent 串行调用多个工具。
3. **完整 Identity**：每个 Agent 均给出 Name、Role、Capabilities（能/不能）、Inputs、Outputs、Dependencies、Decision Boundary、Trace 八字段。
4. **AgentTeams 基线**：方案明确以 AgentTeams 为设计基线，并逐项映射角色编排、任务拆解、上下文传递、协同执行、状态跟踪五种能力。静态兼容不得写成已完成真实集群运行。
5. **Skill 工程**：核心能力以可复用 Skill 表达；至少说明名称/类型、场景、输入、输出、触发、依赖、失败、安全和复用边界。
6. **上下文与状态**：至少展示 memory、RAG、共享状态、Trace 中的两种机制，并说明跨 Agent 如何传递及恢复。
7. **高风险治理**：高风险写操作具备人工审批、权限边界、失败/回滚和审计证据；执行 Agent 不能自批、自验。
8. **证据诚实**：不把路线图写成已实现，不把合成适配器写成真实企业系统，不把 CRD 静态校验写成 `agt apply` 或 Matrix 实跑。
9. **可复核 PoC**：核心主张不能全部停留在概念图。至少有本地可复现闭环、测试/回执/Trace 之一作为运行证据。

## 3. Claim → Evidence 分级

评委 Agent 对每个关键主张标注 E0–E4，按“材料中能看到什么”而不是“作者知道自己做过什么”分级。

| 等级 | 定义 | 可接受例子 | 评审处理 |
|---|---|---|---|
| E0 | 只有主张 | “支持回滚”“可跨行业复用” | 不计为完成；列为风险 |
| E1 | 静态说明 | 架构图、字段清单、接口/Skill 契约、CRD YAML | 证明设计存在，不能证明运行有效 |
| E2 | 作者可复现 | 本地脚本、自动测试、Golden/攻击用例、可运行演示 | 可计工程完成；记录复现入口 |
| E3 | 独立可核验 | 实际工具回执、Trace hash-chain 校验、审计包 manifest、独立 Verifier 结果、干净环境复跑 | 核心竞争证据；优先出现在初赛材料 |
| E4 | 外部或生产近似证据 | 公开 Release、真实 AgentTeams/Matrix handoff、真实沙盒/用户试用、第三方验收 | 强加分证据；没有时必须诚实写路线图 |

分级规则：同一主张只取材料中最高的、可定位的证据等级；截图若无法定位来源或复现，只按 E1；未来计划一律不高于 E0。关键差异化主张“携证执行”至少应达到 E3。

## 4. 评分与内部阈值

先过 Must-pass，再按官方五维权重逐项打分。每个维度同时记录：`得分 / 主要证据 / 最大反证 / 下一项最小改进`。

内部决策阈值如下，**不是 GOAI 官方分数线，也不代表实际晋级概率**：

- `82–100`：强竞争版本；允许提交，但仍需清除所有 P0。
- `75–81`：边缘竞争版本；必须优先补材料可见证据，不宜继续扩功能。
- `<75`：不建议冻结；返回最大失分维度整改。
- 任一 Must-pass gate 失败：无论总分多少均为 `NO PASS`。

概率估计必须给区间和置信度，不得给单点承诺。至少分两种阅读情形：仅看必交介绍+方案，及评委实际复现选交代码。若两者差距超过 10 个百分点，说明必交材料证据不足。

## 5. 五分钟质询协议

评委 Agent 在不查看作者口头补充的情况下先读 500 字介绍和方案，再按下列节奏质询。每个回答必须落到一个文件、页面、运行结果或明确的 GAP。

| 时间 | 质询 | 通过标准 |
|---|---|---|
| 0:00–0:40 | 你解决的具体高风险流程是什么，谁为它付出成本？ | 能给出用户、触发事件、当前断点和可观测结果，不只说“提升效率” |
| 0:40–1:25 | 为什么必须是多 Agent，而非一个 ChatGPT 加工具？ | 四类决策权相互制约；执行者无审批权，验证者无写权限 |
| 1:25–2:10 | AgentTeams 在哪里，不使用它会失去哪五种能力？ | 五能力逐项映射；静态兼容与真实运行状态分开陈述 |
| 2:10–2:55 | Skill 如何复用，失败、安全和依赖边界是什么？ | 指向核心 Skill 契约及跨场景不变层/适配层 |
| 2:55–3:45 | 如何证明审批绑定了实际工具参数，且执行者不能自证？ | 展示 ECP、服务端重算参数 hash、签名审批、ToolReceipt、独立 VerificationReport |
| 3:45–4:25 | 拒绝、崩溃、重放或并发时会怎样？ | 能展示阻断、幂等、checkpoint、恢复/回滚与 Trace 证据 |
| 4:25–5:00 | 哪些是今天真实完成，哪些仍是路线图？ | 明确 Local PoC、静态 CRD、合成适配器、真实 Matrix/ERP/SSO GAP |

立即追问项：

- 删除 Planner 后系统为何不等价？删除 Verifier 后有什么新增风险？
- Human 审批签署的究竟是自然语言，还是具体计划与参数？
- 政策更新后旧审批为什么不能重放？
- 第二业务场景复用了哪些代码/Skill，替换了哪些适配器？
- 审计包能否证明“实际执行参数”而不是“计划参数”？

## 6. 每阶段输出格式

```text
Verdict: PASS / CONDITIONAL PASS / REVISE / NO PASS
Must-pass: n/n；P0: [...]
Score: 场景 x/25，多Agent x/25，Skill x/25，工程 x/20，开源 x/5，总分 x/100
Evidence: E0=n, E1=n, E2=n, E3=n, E4=n
Preliminary pass estimate: [low%, high%], confidence=[low/medium/high]
Top 3 risks: ...
Smallest next improvements: ...
Unsupported claims to delete: ...
```

最终复核顺序固定为：只看必交材料一次 → 再看选交代码与运行证据一次 → 对比差异 → 输出区间。评委 Agent 只读，不直接修改项目，避免“自己出题、自己改答案、自己判满分”。
